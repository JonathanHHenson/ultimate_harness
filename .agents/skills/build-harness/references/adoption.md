# Research and Plan Harness Adoption

Read this guide when installing or evolving a harness. Use the portable package that invoked the workflow as the base and treat the target repository as a separate input.

## Before designing the plan

Read [Learn a Topic](../../learn-a-topic/SKILL.md) and its [research and Socratic inquiry procedure](../../learn-a-topic/references/research.md) before drafting. Apply that procedure to both investigations. Keep notes and proposed changes in a private workspace outside the target. Corroborate a consequential assumption or apparent contradiction against the closest reliable source or a safe local check, and record what is observed, inferred, or still open.

| Investigate | Evidence to collect |
| --- | --- |
| Base harness | Read the entire bundled export catalog. Inspect each component's instructions and the relevant script contracts. Trace how agent entry points route to contextual instructions, skills, feature memory, and validation. Identify portable component dependencies, prerequisites, the state each component owns, and which project-specific routes the adopter must supply. |
| Target's technical context | Identify the repository and applicable root, inherited, and scoped instructions. Inspect architecture, source layout, languages and versions, dependency and runtime setup, tests, CI and deployment, local and hosted agent integrations, and documentation. For an existing harness, map ownership of instructions, validation triggers, exact commands, stored state, and consumers of current paths and interfaces. Corroborate active behavior with configurations, tests, or safe read-only observations. |
| Target's team and project context | Learn the purpose, users, maintainers, contribution and review process, delivery and release habits, team terminology, operational constraints, and applicable policy. Use the README, contributor docs, glossary, runbooks, decision records, and available evidence from the human. Confirm details that materially affect the plan when documentation is missing, stale, or contradictory. |

Before presenting recommendations, explain how each capability would operate in this target. Check a typical task, an unrelated task, and an overlap where several rules apply. Challenge assumptions about whether a documented workflow still runs, whether an apparent equivalent covers the same behavior, and whether a proposed check can work in the target's normal environment. Present unresolved choices and material uncertainty to the human. Keep research and decision summaries free of secrets and unnecessary private data.

## When tailoring the recommended plan

- Account for every portable component in the research notes. Record what it does, the observed target fit, the recommended action, and any dependencies, changed behavior, or prerequisites. Use the catalog's `requires` for intact copies. For a native alternative, show what behavior it supplies and adapt the dependent paths and guidance.
- Ask separately about availability and activation where each is a meaningful choice. For example, keep the decision to include Copilot reviewer instructions separate from activating hosted review. Describe routine wiring that follows directly from an approved choice as part of its effect. Show the consequence of each meaningful exclusion or modification.
- Propose additional **skills** for evidenced recurring work or gaps in project language coverage. For each proposal, cite what you observed, name the repeatable task and intended trigger, and state its expected outcome. Reuse or extend existing guidance when it solves the need. Give each proposed language skill its own decision. A skill for a shared tooling workflow can cover several formats and serves a separate purpose from language coverage. Use [Learn and Build Skills](../../learn-and-build-skills/SKILL.md) to author approved skills, including its [language skill workflow](../../learn-and-build-skills/SKILL.md#when-authoring-a-language-skill).
- Propose additional **validation rulesets** for evidenced risks the current checks leave open. For each proposal, describe the trigger, what it should catch, the available tool or review action, and the success evidence. Check that the required environment is realistic. Use the [validation authoring standard](validation.md) for approved rules. Evaluate proposing a skill and proposing a validation ruleset as separate decisions even when both support the same area. If research supports no new item in one category, state what was checked and why the existing coverage is sufficient.

## When collecting decisions

- Run the bundled [Human Interaction skill](../../human-interaction/SKILL.md) directly from the built package before editing the target. Prepare every answerable decision for the initial question set. If a prerequisite only determines whether an answer applies, include the conditional preference in that set. For example, ask “If the feature merge check is installed, should CI run it?” Offer “Run the feature merge check in CI” and “Keep the feature merge check local” as a separate question from installing the check.
- Map every portable component to its own answer field or to an explicit decision the human has already made. Use the catalog key as the stable field ID for each unsettled component. Give each field one effect the human can accept or decline. Keep design interview activation, review routing, hosted reviewer activation, CI wiring, ledger linkage or migration, each proposed skill or validation ruleset, and each proposed third-party import separate where open. For example, offer adding feature records and linking them to an existing ledger as separate choices. The option to add records should leave the links to the separate decision. Group related fields under short headings and omit single-option fields that only acknowledge a settled constraint.
- Use an adaptive follow-up only when the actual answers expose a material decision whose options could not be offered in the initial question set. For example, ask if a selected integration lacks a required capability and there are multiple ways to resolve the conflict. Apply conditional preferences only when their stated prerequisites were approved and are satisfied. An answer about activation cannot approve a declined prerequisite. When the answers settle the scope, summarize it and finish the exchange.
- Review the draft using [the decision-page instructions](#before-showing-a-design-decision-page).
- Use the same separate questions in either delivery format. When the human chooses a form, use one submission for the initial set and follow the skill's [form handoff](../../human-interaction/SKILL.md#when-the-human-chooses-a-form).
- Carry forward explicit, applicable decisions. Keep the full proposal as the recommendation and distinguish it from an approved change. Never treat an unanswered required choice, an expired form session, or a displayed recommendation as agreement. Show the resulting scope and any newly exposed choices before implementation. Get confirmation if the resulting change includes unsettled impacts or materially differs from what the human agreed.

### Before showing a design decision page

1. Keep the Markdown prologue to a few short paragraphs. State what the submission decides, the constraints already settled, and one concrete example from a routine target task. For evolution, show today's workflow and what the recommendation would change. Keep the detailed research and catalog mapping in the notes, and put decision-specific evidence next to the affected field.
2. Give each question a short label. Read **each visible option label on its own**, including the recommendation and every alternative. Name the affected capability, workflow, or path and say what selecting it adds, changes, keeps, or skips. Include only alternatives with a distinct practical effect. Prefill a supported recommendation with `default` and collect approval through the submitted answers. Add help text when the human needs a reason, consequence, prerequisite, or approved source and pin to decide. Avoid repeating the same text in the question, options, and help.
3. Reject labels that could be pasted into an unrelated decision unchanged. For example, use “Block pull requests while features are unfinished (Recommended)”, “Run the feature merge check locally”, or “Have reviewers verify feature completion manually” when those are distinct choices. For ledger integration, use “Link feature records to council tickets and keep the council ledger authoritative”. Apply the same standalone reading test in chat.
4. Before publishing, run the form CLI's schema check, then run `python <bundle-root>/.harness/scripts/check_adoption_options.py <page.json>` with the same Python 3.11+ interpreter. The [option check](../../../../.harness/scripts/check_adoption_options.py) reports a field ID and option value for stock or repeated labels. Rewrite every flagged option and rerun it. Check the remaining labels for project-specific effects yourself. Repeat for every next page and every revision in response to a clarification request before sending it.
5. Read the full page as a maintainer. Keep each unsettled decision independently selectable. Carry explicit choices into the summary and ask again when new evidence materially changes their implications. On follow-up pages, explain what prompted the round and reuse context the human already has.

## When wiring and verifying approved capabilities

- Copy approved portable material, preserving paths or updating every affected caller. Before writing, recheck the affected paths and incumbent rules against the agreed scope. Author or amend the target's concise [agent entry points](agents-md.md), [validation routing](validation.md), language skill index, contributing documentation, and ignore rules using the target runtime and tooling. Point to real checks and installed references. Route code changes through code and security review, configuration-only changes through security review, and prose-only changes through applicable documentation checks when both reviews are adopted. Keep target-specific review guarantees when merging.
- When adopted, isolate Python with the [harness environment](python-environment.md) and route setup before its helpers. Merge ignore rules for `/.scratch/`, `/.harness/.venv/`, `/.harness/.venv.lock`, `/.harness/.uv-cache/`, and Python bytecode as applicable. Track dated feature records and project documentation for decisions and verification. Within the feature store, ignore `.locks/` and per-feature `.status-pending.json` and `.write-*` files. Adapt paths when the target uses different conventions. Verify the standalone feature merge check when installed. Connect hosting or CI integrations as agreed with the human.
- Verify matching, unrelated, and overlapping changes through their active entry points. Run available commands for both new and retained behavior. Test a proposed record migration on a copy and confirm preservation, rollback, and caller compatibility before making an approved live change. Report unavailable checks and outstanding choices explicitly.
