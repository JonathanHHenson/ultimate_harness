# Comprehensive harness adoption

## Research and open questions

The entry points currently recommend a small setup or one increment. The catalog already exports all 19 components and declares intact-copy dependencies. The builder does not select components for adopters. Both research and structured feedback already ship in each package, and both can run before a target harness exists.

The catalog and source contracts establish what is portable. This project's `AGENTS.md`, validation index, language routes, project records, and settings belong to this checkout. Adopters must author equivalent routing for their own context. An existing target's active rules and documented decisions can outweigh a generic recommendation about layout, even when the catalog's full set remains the right starting point.

An unconditional copy risks broken triggers, colliding helpers, or rewriting a team's safety controls. Asking the user to select everything from scratch repeats work the agent can do from evidence. Use a full baseline, separate decisions only where scope or behavior can change, and an explicit reconciliation for overlapping practices. A file match alone cannot establish equivalent behavior.

## Requirement coverage and technical approach

- **RESEARCH.** Both packaged entry points explicitly invoke bundled Learn a Topic and a common Build Harness reference. The reference defines a read-only inventory for the portable base and technical and team context, with corroboration, safe local checks, open questions, and project-specific opportunities.
- **INSTALL.** Walk every catalog component and propose adoption by default. Plan target-owned entry points and wiring. Route unsupported, costly, unwanted, or ambiguous options through structured feedback, with the recommended adaptation and consequences given separately.
- **EVOLVE.** Compare each component's intended behavior with the incumbent capability. Preserve verified equivalents, integrate gaps, merge overlaps, and propose replacing a specific conflicting part when the alternatives are unsound. Keep human decisions independent, retain unaffected behavior, and test migrations on copies before changing live state.
- **DECISIONS.** Use the existing local form with an independent field per unresolved material decision and separate approval per new skill or validation. Explain evidence, impact, dependencies, and meaningful alternatives. Follow up when an earlier choice exposes a new decision. Preserve settled answers and do not interpret abandonment, defaults, or a missing answer as consent.
- **PORTABILITY.** Export the shared reference inside the existing `harness-maintenance` component. Use package-relative links from both entry points and reference-relative links to reusable standards and skills. No change to the builder, runtime, or archive layout is needed. Keep source-project data outside portable assets.

## Verification strategy

Build and extract both packages. Check reference and dependency resolution and rerun the builder tests. Use separate first-install and incumbent projects to exercise actionable forms, inspect the target-specific proposals, and trace resulting routes. Use a partially documented target for the boundary case. Distinguish the live form runtime smoke test from a manual workflow walkthrough or independent-agent trial.

## Interactive handoff follow-up

- **DECISION-COVERAGE.** Require the detailed research method explicitly in the shared guide. Map one stable answer ID to every unsettled component and additional material change. Reconcile the mapping before launching the form. Expose CI integration apart from installing the standalone check. Dependencies can generate a follow-up without removing the initial decisions.
- **FORM-PREFLIGHT.** Reuse the existing page loader and validator in a read-only `check` command, with the same workspace rules and errors as `serve`. Field limits belong in the schema reference. Test the public command on valid and invalid pages and check that it creates no session.
- **LIVE-HANDOFF.** Publish the link while the interactive agent can continue polling, verify the page is live, use bounded response waits and verify confirmation at the end. When the runner cannot keep a form available, use structured questions in the conversation. Do not detach an unowned server. Run two fresh interactive Codex sessions on the existing synthetic fixtures and use an independent browser to submit choices; compare the saved replies with the agent's interpretation and verify target hashes.

## Decision-page retrospective

- **FIRST-ROUND-CLARITY.** Both live clarification trials reached the intended skills and preserved answers. The first drafts still made the human translate catalog terms and policy-heavy prologues. Add a shared readability review before the first decision page and subsequent material rounds. Put a representative project task and its proposed effect ahead of the detailed inventory, and tie each option to a concrete consequence. Continue to verify field coverage, independence and schema with the existing process.

## Make every answer describe its effect

Apply the same standalone reading test on every install and evolve page and in the conversational fallback. The visible answer names the affected behavior, path, or workflow and what choosing it changes or preserves. The question and help text can carry rationale and context. A small adoption-specific check rejects known generic wording and labels copied across decisions. Keep the form schema reusable and have the agent review project relevance and clarity after the mechanical check. Run the checker on the rendered payload before serving or replacing a page.

## Unify installation and evolution

The two packages ship the same export catalog and payload. Keep one `install-harness` entry point. Research the bundle and target once, then select installation for a first harness or evolution for a target with active guidance, check routing, or records. Keep the mode-specific planning steps in focus. The common steps still require a full adoption proposal, individual human decisions, preflighted forms, separate installation and activation decisions, and evidence before handoff.

Build one payload and one archive from the catalog. Preserve its paths, exclusions, permissions, and protection of an existing payload on a failed build. Document the single package for future releases and keep historical verification tied to the version it exercised.

Compare the separate and merged packages on the same synthetic first-install and evolution targets using fresh interactive sessions. Check the first and follow-up forms, confirmations, target constraints, and preservation of target files during planning. Exercise applying approved material on disposable targets separately from form handoff. Record the conditions each check covers.

## Keep adoption forms concise

Keep the detailed catalog mapping in research notes. Lead with the decision scope, settled constraints, and one ordinary project task. Give each unsettled component and additional material decision a separate field. Ask known conditional preferences on the first page and apply them only when their prerequisites are approved and satisfied. Use another page when actual answers create a material choice whose options could not be offered initially. Summarize settled answers and close the form.

Compare the previous merged package and the revised package in fresh interactive sessions on matched targets. Count visible words, pages, fields, and options. Check field coverage and independence, research, page preflight, browser handoff, accepted answers, and target digests.

## Invoke Grill With Docs before either plan

Require direct invocation from the shared portable entry point after research and before either route drafts a plan. Use the package's pinned copies. When a skill tool cannot invoke those copies, open Grill With Docs, Grilling, and Domain Modeling directly. Keep interview tailoring in the existing contextual instructions. The target stays read-only during planning, and consent to install the interview workflow only governs future target work.

Before form preflight, check that the human can approve each independently useful validation trigger or effect. Keep proposed checks for code changes separate from checks for operational work even when they use the same evidence.

Rerun the matching first-install and existing-harness trials in fresh interactive Codex sessions. Verify successful loads before form preparation and inspect how the proposed interview choices reflect target rules and terminology. Check one submitted page per route when answers settle scope, independent choices, browser confirmation, and unchanged target digests.
